# QueryVerdict competitor and feasibility research

- **Research date** 2026-11-25 (Asia/Kolkata)
- **Status** Research complete for the planning review. Recommendations require maintainer approval.
- **Recommendation** **CONDITIONAL GO** for an evidence-first join debugger and a scoped feasibility spike.

## Executive summary

The browser SQL workspace is a crowded category. Duck-UI, PondPilot, dbxlite, and SQL Workbench already cover local file exploration and SQL execution. SQL Workbench can visualize an executed DuckDB plan. The closest functional competitor, SQL Viewer, already runs DuckDB-WASM in the browser, shows intermediate relations, and lets users step through joins and filters. A local editor, a JOIN diagram, and stage-by-stage inspection are established capabilities. [Duck-UI](https://github.com/caioricciuti/duck-ui) · [PondPilot](https://github.com/pondpilot/pondpilot) · [dbxlite](https://github.com/hfmsio/dbxlite) · [SQL Workbench plan viewer](https://sql-workbench.com/docs/visualizing-query-execution-plans/) · [SQL Viewer](https://github.com/web-tollings/sql-viewer)

QueryVerdict has a narrower opportunity. Help an analyst answer **“Which join changed the grain of my result, which keys explain the change, and can I reproduce that finding in SQL?”** Start with two local relations, explicit equi-join keys, measured multiplicity and unmatched rows, and a declared result grain. Show the matched, multiplied, and dropped keys with reproducible counts. Allow a user to export the diagnostic SQL for use in their normal environment, with an explicit DuckDB dialect label. Treat natural data variation as evidence and reserve defect language for a known requirement. Semantic layers already offer fan-out protection using declared relationships, and dbt already offers data and unit tests. The opportunity is the interactive workflow before the user has a model or test in place. [Looker symmetric aggregates](https://docs.cloud.google.com/looker/docs/best-practices/understanding-symmetric-aggregates) · [Lightdash joins](https://docs.lightdash.com/semantic-layer/joins) · [dbt data tests](https://docs.getdbt.com/docs/build/data-tests) · [QueryVerdict findings taxonomy](../AGENTS.md)

The evidence supports investigating that workflow. It does not establish demand for a separate product, a market size, or a supported dataset limit. Production approval should depend on the tool beating manual SQL and the closest browser debugger in observed tasks, with a pinned engine passing privacy, correctness, cancellation, and browser checks on a Pages-style deployment. A reusable SQL fixture corpus and a reproducible benchmark are valuable evidence of engineering practice even if the product hypothesis fails.

## Market gap and positioning

**Primary user hypothesis.** An analytics engineer or SQL-heavy data analyst receives a suspicious count or amount, can bring a representative local snapshot, and needs an explanation before changing a dashboard, opening a pull request, or adding a model test. Existing workarounds are ad hoc GROUP BY and anti-join queries, inspecting one CTE at a time, or defining cardinality in a model that already exists. The highest-value comparison is a well-prepared manual SQL audit plus SQL Viewer.

**Secondary user hypothesis.** Reviewers, educators, and maintainers can use synthetic demos to teach and review join bugs. This audience is easier to reach and can supply reproducible fixtures. It may also have less recurring professional need. Treat evidence from it separately from evidence from working analysts.

**Positioning.** QueryVerdict is a private, browser-based join debugger that shows which keys multiplied or disappeared, checks a grain you declare, and gives you SQL to reproduce the finding.

**Proposed USP.** One short workflow combines locally measured key-level evidence, explicit analytical intent, and a portable explanation. The observed sources establish each ingredient in adjacent tools. They did not establish the complete workflow in the compared browser products. The claim to validate is a faster, more trustworthy path from a suspicious result to a defensible diagnosis.

**Counterarguments.** Teams often cannot export representative warehouse rows even to a local-only browser. Their data may be too large, access policies may forbid moving it, or the bug may involve dialect-specific syntax. Senior analysts can write three diagnostic queries quickly. Junior analysts may not know the expected grain, which would cap the verdict at a suspicious pattern. A browser debugger that forces analysts to reconstruct many joins can lose time to import and remapping. Large enterprise CI, data observability, and warehouse editing are poor entry markets under the project constraints.

## Algorithms and correctness model

### Exact multiplicity for the supported join

Group the two join inputs by the full key using the same comparison semantics as the instrumented join. For a matchable key k, let L(k) and R(k) be the input row counts. If R(k) is zero, the left key is unmatched. An inner equi-join produces L(k) × R(k) matched pairs for k. A left equi-join produces L(k) × max(1, R(k)) rows for a left key. Count unmatched left rows separately, including rows whose join key cannot match. Compute excess copies of left rows as L(k) × max(0, R(k) − 1). The difference between total inner-join output and total left input equals excess copies minus left rows lost. A net change of zero can therefore conceal both a loss and a fan-out. Use a wide integer type and surface overflow as incomplete analysis. [DuckDB JOIN semantics](https://duckdb.org/docs/stable/sql/query_syntax/from)

For standard equality, any NULL in a composite key makes the comparison unknown and prevents a match. A grouped NULL bucket still exists in the profiling query and must be accounted for explicitly. A null-safe predicate such as IS NOT DISTINCT FROM changes match eligibility and belongs behind its own coverage definition. Mixed-type keys, collations, expressions, OR conditions, and extra ON predicates can invalidate a naïve frequency product. Initially accept simple column equality with compatible types and verified comparison semantics. Produce the logical input relation and keys from the parsed scope or ask the user to select them explicitly. [DuckDB NULL semantics](https://duckdb.org/docs/stable/sql/data_types/nulls.html) · [DuckDB comparison operators](https://duckdb.org/docs/stable/sql/expressions/comparison_operators.html)

**Worked example.** Left has A=2 and B=1. Right has A=2 and C=1. The inner join returns four rows from A, adds two copies relative to A’s two input rows, and drops B’s single row. Its net increase versus the three input rows is one. The left join adds a null-extended B row and returns five rows. Right key C is unmatched. A declaration of one output row per join key would make A a demonstrable violation in both outputs. An intended relationship retaining all four pairs makes those pairs valid.

### Loss, duplicates, and aggregation

| Check | Method | Boundary and prior art |
| --- | --- | --- |
| **Unmatched rows and downstream row loss** | Use grouped counts plus a keyed anti-join or NOT EXISTS for witness keys. For supported later filters compare membership at defined logical stages using stable identities or explicitly labelled multiplicities. | Prefer a marker independent of nullable business values to identify outer-join matches. A NULL in a projected right column could come from a matched right row. Avoid NOT IN for NULL-sensitive loss diagnostics. Do not attribute optimizer filter pushdown to the author’s clause order. [DuckDB semi and anti joins](https://duckdb.org/docs/stable/sql/query_syntax/from) |
| **Duplicate keys and NULLs** | Use GROUP BY over all selected key columns, COUNT(*) and HAVING COUNT(*) > 1. Record COUNT(*) versus COUNT(column), number of duplicated keys, rows in duplicate groups, and excess over one per key separately. | Keep uniqueness and non-nullness as distinct policies. A detected duplicate is an observation unless a compatible key or output grain requires uniqueness. dbt tests provide familiar equivalents. [dbt data tests](https://docs.getdbt.com/docs/build/data-tests) |
| **Additive measure impact** | Compare weighted sums of the measure at its source grain before and after join multiplicity. For INNER use each source row’s match count as its weight. For LEFT use at least one. Aggregate source contributions by verified key where the predicate permits it. Preserve SQL SUM semantics for NULL and empty input. | A sum delta may be negative, zero through cancellation, or masked by filters. AVG, COUNT DISTINCT, balances, ratios, and percentiles need different contracts. SUM(DISTINCT measure) collapses equal values from different entities. Pre-aggregate detail tables only when measures and filters make the rewrite valid. [Looker symmetric aggregates](https://docs.cloud.google.com/looker/docs/best-practices/understanding-symmetric-aggregates) · [PostgreSQL double-counting example](https://www.postgresql.org/message-id/86b9ec78-925c-1935-bc9d-6bad4ceb1f40%40illuminatedcomputing.com) |
| **Version comparison and regression fixtures** | Use bidirectional EXCEPT ALL when comparing compatible output multisets and order is out of scope. Use key-based comparisons only after establishing uniqueness and defining NULL, tolerance, and comparison policies. | Equality on a snapshot is snapshot evidence. Cosette and VeriEQL have formal approaches over declared fragments and bounds. They solve a broader equivalence problem than this MVP. [DuckDB set operations](https://duckdb.org/docs/stable/sql/query_syntax/setops.html) · [Cosette](https://cosette.cs.washington.edu/) · [VeriEQL](https://arxiv.org/abs/2403.03193) |
| **Plan and logical stages** | Optional EXPLAIN or EXPLAIN ANALYZE can add estimated and actual operator counts where verified. Use explicitly regenerated diagnostic queries for logical stages. Document which run each metric came from. | EXPLAIN ANALYZE executes a query. Optimizer joins, predicate pushdown, projections, and eliminated operators do not correspond one-to-one to authored SQL stages. [DuckDB EXPLAIN ANALYZE](https://duckdb.org/docs/current/guides/meta/explain_analyze) · [Principles of Query Visualization](https://arxiv.org/abs/2208.01613) |

**Verification strategy.** A known-answer corpus should include intended many-to-many and unwanted one-to-many cases, clean one-to-one, orphan keys on both sides, repeated NULLs, composite keys, empty relations, decimal and negative measures, fan-out with net-zero sum, and simultaneous fan-out and row loss with identical before/after row counts. Include a LEFT JOIN with a NULL-rejecting WHERE and cases where a nullable right value belongs to a genuine match. Compare generated probe results to direct materialized joins on small fixtures. Add deterministic randomized fixtures to cross-check frequency formulas. For unsupported syntax and interrupted, partial, or sampled checks, assert the displayed coverage and severity. Sampled witnesses can demonstrate existence in the sample. An absence of sampled witnesses cannot establish that the complete relation is clean.

For this report, an in-memory SQLite check reproduced the worked example and cross-checked the inner join, left join, and unmatched-left count identities against 200 deterministic single-key fixtures with duplicates, NULLs, and empty inputs. This check covers the documented identities over the tested inputs. DuckDB-WASM behavior, composite keys, performance, and product integration still require a separate spike.

## Browser-only feasibility

**Verified capability.** DuckDB-WASM implements an asynchronous browser SQL engine with local file registration and Arrow results. Its documented APIs distinguish complete result materialization from streaming record batches. Its baseline single-thread bundle can run without cross-origin isolation. The threaded bundle requires isolation. The current deployment docs use base/threads naming and describe former names. Pin a release and test its assets because bundle names, native code, and extension support can change together. ### Feasibility experiment design

- **Reference hardware.** Use the approved Apple M2 MacBook Air with 8 GB RAM and the 50 MB, 200 MB, 500 MB, and 1 GB inputs. Record whether the advertised size is total input or per relation, compressed bytes, decoded types and widths, row counts, key skew, format, browser/OS/build, commit, exact query, and generated seed. Include narrow and wide data, uniform and skewed keys, small and large outputs, CSV and Parquet. Keep generated datasets outside Git. [Project decision log](DECISIONS.md)
- **Observe the workflow.** Record cold/warm startup, time to first interactive evidence, whole diagnostic latency, responsiveness, peak memory by available instrument and scope, and worker recovery. Capture repetitions, median and tail observations with sample count, failures, missing metrics, and the cause where known. A missing memory metric remains missing. Keep the whole test tab usable, including after failed work. Start with single-threaded deployment and no OPFS dependency.
- **Proposed minimum experiment.** Before production approval, pass the complete local demo across the three desktop browser families and run the representative 50 MB join audit repeatedly on the reference hardware. Set a proposed acceptance target of a responsive Cancel control and recovery within two seconds of requesting cancel or initiating the worker fallback under the pre-agreed stress case. Treat 200 MB as stretch qualification and 500 MB/1 GB as boundary characterization until measurements justify more. This is a proposed test gate, with zero measurements in this report.
- **Use the deployment artifact.** Test a Pages-style project path, asset MIME and URLs, same policy in the worker, disabled third-party network access, deterministic recovery, and baseline query support. Local dev-server performance and permissive headers are insufficient evidence for the production artifact.

### Can GitHub Pages meet the cost and privacy constraints?

**Verified hosting fit.** GitHub Pages supports static sites from public repositories on GitHub Free. GitHub-hosted standard Actions runners are free for public repositories. Pages documents a 1 GB published site limit, a 100 GB monthly soft bandwidth limit, and deployment constraints. Vite’s guide documents building for a repository subpath. Public static hosting can therefore meet zero mandatory recurring costs within the service’s terms and limits. A domain purchase, CDN, custom header proxy, paid runner, and hosted data service are unnecessary for the proposed baseline. [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) · [Actions billing](https://docs.github.com/en/actions/concepts/billing-and-usage) · [Vite static deployment](https://vite.dev/guide/static-deploy)

**Unverified deployment details.** Do not depend on adding COOP/COEP response headers or on cross-origin isolation for the baseline. DuckDB documents that its threaded bundle requires these headers, and GitHub’s public Pages discussion illustrates the custom-header constraint. Verify the actual release endpoint and worker behavior when the maintainer approves a spike. Use a dedicated Pages origin if tests establish a need for stronger storage or script separation from other same-origin project sites. Keep demo assets small, vendored and licensed. Hosting receives normal static asset requests and host-level traffic metadata. Do not make broader claims about the host’s own logging. [DuckDB bundle deployment](https://duckdb.org/docs/2.0/clients/wasm/deploying_duckdb_wasm#cross-origin-isolation) · [GitHub Pages COOP/COEP discussion](https://github.com/orgs/community/discussions/13309) · [Origin-based storage](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

**Estimate for cost planning.** Approximate cold traffic as compressed critical bytes times cold visits, adding repeat loads and cache misses. For example, a hypothetical 10 MB cold payload served 10,000 times is roughly 100 GB before other traffic, using decimal units. This is an illustrative calculation, not a measured bundle size, forecast, cost, or capacity promise. Measure compressed transfers and use lazy entry points if they materially reduce cold traffic. Static hosts can throttle or change terms. Keep a portable artifact that can be mirrored on a maintainer-approved free static host if needed.

## Adoption and maintenance risks

| Risk | Why it could prevent adoption | How to test or limit it |
| --- | --- | --- |
| **Local sample availability** | Analysts may be unable to export representative data, and synthetic demos can overstate convenience. | Recruit users whose workflows already involve local Parquet or CSV exports. Ask how the last incident was debugged and what could be used within policy. Offer only synthetic fixtures and sanitized reproductions in public. |
| **Workflow overhead** | Preparing files and remapping keys can cost more time than manual SQL. Complex incidents may involve many stages or a dialect mismatch. | Time the complete path from opening a local sample to a valid diagnosis, including import and setup. | **False certainty** | One confident false positive can destroy trust in a product called QueryVerdict. A clean result may be mistaken for overall correctness. | Display inputs, intent, exact evidence, and coverage with every finding. Test negative cases as rigorously as positive cases. | **Engine and browser churn** | Dependency upgrades can change WASM assets, parser shape, file support, memory use, or worker behavior. | **Weak repeat use** | A strong demonstration and many stars may come from learners or drive-by traffic with little professional repeat use. | Track voluntary follow-ups, second tasks, issues with reproducible examples, and outside contributions alongside stars. | **Portfolio distraction** | Rebuilding standard editor, notebooks, charts, and persistence consumes time that could show strong SQL and correctness engineering. | Publish the join audit, fixture corpus, benchmark method, and architecture trade-offs as the main engineering artifacts. | **Support burden and licence confusion** | Users may expect every SQL dialect, browser, file type, or dataset size. ## Decision and validation gates

**CONDITIONAL GO** for user discovery and an explicitly approved feasibility spike. Maintain an independent review of the evidence before making a production decision.

| Gate | Proposed evidence to proceed |
| --- | --- |
| **Demand and comparative usefulness** | Interview eight people in the primary segment and collect recent examples of how they diagnosed the problem. Observe five completing a matched pair of tasks using manual SQL and the proposed flow, counterbalancing order where practical. Also compare one representative case with SQL Viewer. Proceed if at least four of five complete the proposed tasks accurately and at least three show a concrete workflow advantage, such as faster correct diagnosis or reproducible evidence they could not produce within the comparison session. Seek at least two voluntary second trials. These thresholds are screening criteria for a small exercise. |
| **Correctness and trust** | All deterministic fixture expectations pass. In the supported join subset, direct materialized results agree with the contribution probes on known and generated cases. Coverage and finding labels remain accurate on unknown intent, intentional fan-out, unsupported syntax, and interrupted runs. |
| **Privacy and static deployment** | The pinned single-thread build and required assets work at a Pages-style subpath. Browser checks show only approved static asset requests and zero transmission of local canary data or SQL from both app and worker. No cloud backend, mandatory paid service, CDN, custom proxy, or mandatory account is required. |
| **Usability and capacity** | The complete demo works on desktop Chromium, Firefox, and Safari. The pinned qualification workload at 50 MB passes with responsive cancellation and recovery. Publish measured results and limits with the exact method. Start with a narrower support matrix only if its audience still supports the product case and the maintainer approves it. |
| **Maintainer sustainability** | Licence and transitive notice review is complete, benchmark reproduction is documented, the first-release scope fits one maintainer, contributor tasks are clear, and upstream problems have a bounded fallback. |

If users cannot bring realistic samples, the browser workflow fails to improve observed diagnosis, or the static deployment cannot satisfy the privacy and recovery gates, **NO-GO for a standalone general-purpose workspace**. Preserve the public-domain or compatibly licensed fixture design and the research notes as engineering artifacts. If the manual comparison shows value only in education, consider a smaller educational join lab as a separate maintainer decision.
