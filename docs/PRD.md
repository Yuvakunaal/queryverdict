# QueryVerdict production requirements

> **Status** Proposed Phase 5 production specification, 2026-11-26. Maintainer approval is required before implementation. P0 defines the first public release. The browser spike is research evidence, and the release gates below remain open.
>
> **Owners** Product and architecture define the specification. The maintainer approves scope and release. Implementation and independent verification follow [AGENTS.md](../AGENTS.md).

## 1. Vision, audience and positioning

**QueryVerdict** is a free, open-source website for investigating joins in local SQL data. Its first job is to answer **“Which keys multiplied or dropped my rows, by how much, and did that break the join contract I declared?”** A user opens a demo or imports local extracts, writes or pastes a supported join, and gets measured counts, representative keys and reproducible diagnostic SQL. The workspace supports that investigation with an editor, schema preview and bounded query results.

| Audience | Job and release use case |
| --- | --- |
| Primary · Analytics engineers and SQL-heavy analysts working with local exports | Check order-to-customer or fact-to-dimension joins before trusting a report. Trace repeated dimension keys, unmatched facts or an intentionally one-to-many relationship. |
| Secondary · Data engineers and developers reviewing a SQL change | Reproduce a suspected regression with two local extracts, check the expected cardinality or preservation rule, and take labelled DuckDB SQL into a review or local test. |
| Secondary · SQL learners and reviewers using examples | Open a synthetic incident and explain why an INNER join can have both fan-out and row loss even when its net row count stays the same. |

The evidence-backed proposition is **local, key-level join evidence tied to declared intent and reproducible SQL in one workflow**. Browser execution, plan visuals and intermediate-result inspection already exist. SQL Viewer offers stepwise inspection, SQL Workbench offers execution-plan visualization, and dbt and semantic layers already cover tests and declared relationships in their own workflows. The research documented users diagnosing double-counting and missing rows manually. It supports testing this combination for ad hoc investigation. Comparative speed, demand and exclusivity remain unverified. [Competitor research](COMPETITOR_RESEARCH.md#market-gap-and-positioning) · [SQL Viewer](https://github.com/web-tollings/sql-viewer) · [SQL Workbench plan viewer](https://sql-workbench.com/docs/visualizing-query-execution-plans/) · [dbt data tests](https://docs.getdbt.com/docs/build/data-tests)

Success means correct diagnosis with evidence a peer can reproduce, a credible public engineering record, and a support burden one maintainer can sustain. [Project vision](PROJECT_VISION.md) · [Confirmed decisions](DECISIONS.md#confirmed)

## 2. Priority and workflows

- **P0** is mandatory for first public release. A failed P0 criterion blocks the affected release unless the maintainer approves a documented scope change. P1 and P2 do not block P0.
- **P1** improves the established workflow after launch and after qualification. **P2** requires separate product and technical evidence. Stable `QV-*` IDs are never reassigned.
- **Evidence baseline** The independent Phase 4 review found no join-count or matched-row discrepancies in 72 DuckDB comparisons. Type checking, both builds, 80 Vitest, 9 Python and 59 selected Chrome tests passed. That evidence covers the tested spike paths. Safari, Firefox, live Pages, background deadlines and production import-plus-analysis capacity remain unverified. Historical large-file runs are excluded from public capacity claims. [Feasibility checkpoint](FEASIBILITY.md#14-experimental-checkpoint-after-independent-review-step-444-2026-11-26) · [Defect register](SQL_ANALYSIS_FINDINGS.md)

| Workflow | User steps | Observable completion |
| --- | --- | --- |
| Try a known incident | Open the site, load the synthetic demo, inspect the supplied query and run Verdict. Add or remove the example expectation. | Same counts and witnesses on repeat, with a warning under unknown intent and a violation only when the user declares the conflicting rule. |
| Diagnose two extracts | Select two CSV or Parquet files, import them as local session tables, verify names and types, enter one supported join and select **Analyze**. | The report identifies the analyzed inputs, join keys, measured counts, witnesses, expectations and coverage. A key-type mismatch explains how to inspect the schema. |
| Run SQL and reproduce evidence | Use **Run SQL** to see a bounded result. From a separate Verdict report, inspect or explicitly copy the labelled diagnostic SQL. | Running or truncating a query never changes its diagnostic status. A compatible DuckDB session with the same snapshot can reproduce the documented probe. |
| Recover after interruption | Cancel work or receive a limit or engine error. Keep editing, then retry or re-import as directed. | One terminal state per operation. If a worker was replaced, the UI identifies lost tables and stale reports, preserves editor text in the open workspace and allows safe retry. |

### Supported workload envelope

| Axis | P0 boundary or release qualification target |
| --- | --- |
| Runtime | Foreground desktop with a qualified browser/device profile. Test current desktop Chrome, Firefox and Safari at qualification time. Publish the exact versions and operating systems tested and list any unsupported browsers explicitly. A narrower browser release requires an approved scope revision. Mobile and embedded webviews are outside P0. |
| Files and relations | CSV and Parquet local files. Qualify two inputs combined, including mixed formats and import into managed in-memory tables. The goal is **50 MB combined physical input** on the Apple M2 MacBook Air with 8 GB RAM (D-009/P-024). This is a candidate qualification ceiling. Publish the validated envelope per browser and format, including measured decoded width and residency constraints. |
| Work shape | Bounded previews, a simple scan or aggregate, and one INNER or LEFT integer equi-join with a small dimension side. Include single and composite keys, empty and nullable keys, representative wide cells and a skewed-key case. Use safe known-answer fixtures to exercise refusals for high fan-out and over-budget inputs. |
| Support claims | File bytes, decoded data, input rows, key width, join cardinality and operator memory all matter. A compressed file below the file-size threshold can exceed runtime budgets. The release profile must state accepted formats, qualification ceilings, applicable safeguards, and what happens when the workload is declined. |

## 4. P0 Verdict scope and evidence contract

| ID | Requirement | Acceptance criterion |
| --- | --- | --- |
| QV-VER-001 | Analyze exactly one plain SELECT with one INNER or LEFT join between two unambiguous references to stable managed base or temporary tables, without generated columns. Allow table aliases, quoted identifiers, plain columns and `*`. Join keys are direct column references, same-type integers on both sides, supplied through `ON` equality pairs connected by AND or `USING` for one or more named columns. Use only the integer widths qualified on the pinned engine. MVP recognition fails closed on unknown parser shapes or uncertain binding. | Positive fixtures cover INNER, LEFT, aliases, dotted or escaped quoted identifiers, signed/unsigned and wide integers where qualified, and composite keys with NULL components. Negative fixtures cover casts, mixed types, ambiguous names, non-equality predicates, views, CTEs, modifiers, nested queries and unrecognized parser fields. They yield `unsupported` or `inconclusive` with a reason and no authoritative evidence. |
| QV-VER-002 | Measure per-side input rows, NULL-key rows, distinct non-NULL key tuples and duplicate groups, matched and unmatched input rows, dropped rows, multiplied input rows, excess copies, matched pairs and output rows. Label whole-input relationship and matched-key relationship separately, including **No matches** for the latter when appropriate. Show bounded fan-out and unmatched-key witnesses, at most five per kind, with multiplicities and a deterministic order. | Match direct DuckDB results and an independently implemented row-pair oracle for duplicates, NULLs, composite keys, empty sides, skew, one-to-many, many-to-many, and cases where fan-out and loss offset. Verify exact display of counts beyond JavaScript safe-integer precision with small analytic fixtures. Report unmatched left rows in a LEFT join as preserved rather than dropped. Each sample key and multiplicity must agree with the analyzed snapshot. |
| QV-VER-003 | Allow optional join-stage expectations for whole-input key relationship, no row loss by side, no fan-out by side and output row-count bounds. Each declaration has exactly one outcome, `held`, `violated` or `unchecked`, with its identity and affected side or stage. | In a 1-to-many intentional join the same statistics remain observable with or without expectations. Declaring one-to-many holds when evidence supports it; declaring no left fan-out violates when left rows are multiplied. Boundaries for exact row counts are inclusive. For malformed, unsupported, stale or unevaluated declarations, show `unchecked` and why. Across early exits, count and identity match the declarations. |
| QV-VER-004 | Validate evidence in an exclusive, revocable operation on one stable snapshot. Confirm relation identity and key consistency. Validate frequency arithmetic with invariants and an independent match recount, plus executed count and witness identity checks required by the release contract, all within budget. A user transaction may require an explicit refusal. Verdict may bind the original query and run scoped probes. | Tests inject an UPDATE, concurrent registration, removal and replacement, witness mismatch, snapshot mismatch, and an existing user transaction. The report identifies a coherent analyzed snapshot or withholds dependent conclusions. It identifies executed probes separately from ordinary SQL execution and never implies that it ran the original SQL. |
| QV-VER-005 | Fence report publication through final cleanup, lease release and UI delivery. Authority requires a supported query, complete validated evidence and expectations, successful cleanup, current input/query identity and engine generation, and no cancellation. Carry the generation and publication identity or time with the report. | Deterministically inject cancellation, disposal, restart or recovery at each handoff from the last probe through rollback, lease release and presentation. The user receives a terminal cancelled or stale state, with no authoritative measurements or held or violated outcomes from that run. A subsequent data or query change makes a previously valid report historical. A current, uninterrupted run still publishes normally. Closes QV-SA-002. [Defect criteria](SQL_ANALYSIS_FINDINGS.md#qv-sa-002--high--authoritative-report-survives-cancellation-or-engine-replacement-before-publication) |
| QV-VER-006 | Separate diagnostic category, impact severity and coverage. Show checked and unchecked stages and assumptions with every report. A healthy result can say **No issues found in these checks** with coverage. | Golden report tests cover natural fan-out, a valid declared violation, missing evidence, unsupported syntax, SQL errors, probe failure and cancellation. Natural fan-out alone produces no confirmed defect. Incomplete or unsupported reports never render as successful validation, and any retained validated observations are labelled limited evidence. |

### Counting semantics

- A row is matchable only when all equality-key components are non-NULL. Duplicate groups and key relationships concern non-NULL key tuples. NULL-key rows are counted separately and remain eligible for LEFT-side preservation.
- A key occurring `L` times on the left and `R` times on the right contributes `L × R` matched pairs. INNER output is the matched-pair total. LEFT output also includes one row per unmatched left input. An unmatched right row does not contribute output in either supported join.
- Per-side row loss counts input rows that contribute no output. Per-side fan-out counts input rows with more than one output copy; excess copies sum the copies past the first. A net output count can conceal simultaneous loss and duplication.
- Join relationship uses uniqueness on each side. The matched-key relationship describes actual matches and can differ when duplicate keys on an input are unmatched. A relationship expectation states the maximum allowed multiplicity on each side. An observed one-to-one relationship satisfies a one-to-many or many-to-one allowance. A many-to-many allowance imposes no uniqueness constraint. Use the whole-input relationship for this expectation and test the allowed cases explicitly.

### Labels, severity and confidence

| Display category | Severity | Evidence and handling |
| --- | --- | --- |
| Observation | Info | Measured count or relationship scoped to the analyzed snapshot. |
| Suspicious pattern | Warning | Measured fan-out or row loss with unknown intent. Describe impact and expose sample keys. |
| Confirmed issue | Error | Reserved for conflict with a separately established correctness requirement, cited alongside validated evidence. P0 has no independent grain-declaration feature and does not synthesize confirmed issues from measurements. |
| Expectation violation | Error | A user's explicit supported check contradicts complete validated evidence. Identify the rule and measurements. The same event is reported once. |
| Unsupported query, inconclusive check, unchecked expectation | Status | Explain coverage and how to proceed. Distinguish budget exhaustion or missing evidence from an unsupported construct. |
| Query failure or diagnostic failure | Operational error | Attribute the error to execution, parsing/binding or diagnostic execution as appropriate. A failed probe makes no claim about the correctness of the user's result or the success of ordinary SQL. |

Use categorical confidence. **Validated** applies to measured evidence that met its required checks. **Incomplete** applies where a check could not finish or its inputs could not be verified. **Unsupported** indicates coverage outside the contract. Attach this state to relevant evidence and show whether the entire report is authoritative within the defined diagnostic scope. Avoid numeric confidence scores and universal PASS badges. ### Error, loading and recovery states

The state matrix forms part of the acceptance coverage for QV-UI-001, QV-RES-003 and QV-VER-005.

| Condition | Required user-visible behavior |
| --- | --- |
| Starting or recovering | Show the current operation, keep editing available, disable actions requiring an unverified engine, and expose cancellation where work is active. Use indeterminate progress when real progress is unavailable. |
| Importing, running or analyzing | Show the action and input/query identity, separate queued and active work, and keep Cancel reachable. Prevent duplicate requests from repeated activation. |
| Invalid file, unsupported browser, engine boot or policy failure | Explain the specific failure and available retry or supported environment. Never enable an unverified engine. |
| SQL syntax, binding or execution failure | Show the relevant error and preserve SQL text. Identify the affected action and keep any prior report visibly historical. |
| Unsupported diagnostic, invalid expectation or cutoff | Name the construct, constraint or guard that stopped analysis. Give the affected check an explicit coverage state and every declaration an outcome. |
| User cancel, timeout, replacement or disposal | Settle once. Discard subsequent replies. Show whether the engine is usable, recovering or failed. Any old-generation evidence loses authority. |
| Recovery succeeds after termination | Refresh the dataset inventory. Imported tables need explicit re-import; SQL-created session tables may need to be recreated. Keep the editor text in the current workspace. |
| Recovery fails or resource ceiling is reached | Give a clear cause where known and offer retry, smaller input or restart. Document that a browser or OS killing the tab can lose the entire session. |

## 7. Explicit exclusions and roadmap

The P0 analyzer excludes RIGHT/FULL/CROSS/ASOF/NATURAL joins, join chains, non-equality or null-safe predicates, casts and implicit coercions, text or collated keys, expressions and aggregates, `WHERE`, `GROUP BY`, `HAVING`, `QUALIFY`, `DISTINCT`, `ORDER BY`, `LIMIT`, windows, set operations, subqueries, CTEs, views, table functions, generated columns and ambiguous or external relations. It also excludes result-grain checks, metric preservation, aggregate-inflation attribution, automatic rewrites, and claims about business correctness. Ordinary SQL execution follows QV-SQL-001. P0 file support excludes JSON/NDJSON, spreadsheets and database-file uploads. File-backed attach, durable workspaces, notebooks, dashboards, collaborative links and multi-dialect SQL are outside P0.

| ID | Priority | Capability and entry criteria |
| --- | --- | --- |
| QV-ROAD-001 | P1 | Add workflow improvements only where users repeatedly need them, such as syntax suggestions or richer local evidence export. A UX task comparison must show a clear improvement and the feature must preserve accessibility, budgets and the runtime network policy. |
| QV-ROAD-002 | P1 | Evaluate JSON/NDJSON and optional demand-read file-backed tables for **ordinary SQL**. Verify format parity, worker cleanup, explicit resource limits, and recovery against the release matrix. File-backed diagnostics require a proven file-stability contract. |
| QV-ROAD-003 | P2 | Evaluate post-join filter attribution, more join forms, text keys and grain expectations in separate slices. Each slice needs engine-semantic evidence, supported and refused fixtures, resource qualification and independent review. |
| QV-ROAD-004 | P2 | Consider metric preservation only after QV-SA-004 is closed. Require a governed metric contract, exact finite tolerance for exact types or an explicit unchecked result, and independent NULL, non-finite and precision tests. |
| QV-ROAD-005 | P2 | Consider local-only workspace persistence and additional visual debugging only after evidence of repeat need, a storage/clean-up threat model, and a sustainable maintenance plan. |

Website-only delivery, local processing, free and open-source access, zero mandatory recurring infrastructure costs, and the absence of cloud backend, hosted database, mandatory paid API or LLM remain constraints across the roadmap.
